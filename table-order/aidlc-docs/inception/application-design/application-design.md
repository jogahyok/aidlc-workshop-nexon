# Application Design — 통합 문서

## 1. 아키텍처 결정 요약

| 결정 항목 | 선택 | 근거 |
|-----------|------|------|
| 백엔드 구조 | 도메인별 마이크로서비스 | 독립 배포/스케일링, 도메인 분리 |
| 프론트엔드 구조 | 모노레포 | 공통 컴포넌트 공유, 별도 빌드 |
| 데이터 접근 | Raw SQL + 데이터 매퍼 패턴 | 쿼리 최적화 용이, DB 제어력 높음 |
| 서비스 내부 통신 | 직접 함수 호출 | 단순성, 디버깅 용이 |
| 서비스 간 통신 | HTTP/REST | 마이크로서비스 간 표준 통신 |
| 실시간 통신 | SSE | 서버→클라이언트 단방향, 구현 단순 |
| 상태 관리 | React Context + useReducer | 가벼움, 추가 의존성 없음 |

## 3. 컴포넌트 요약

### 백엔드 (4개 마이크로서비스 + 1 게이트웨이)
- **Auth Service**: 인증/인가, JWT 관리, 로그인 시도 제한
- **Store Service**: 매장/테이블/세션 관리
- **Menu Service**: 메뉴/카테고리/옵션 CRUD, S3 이미지
- **Order Service**: 주문 CRUD, 상태 관리, SSE 스트림, 이력 관리
- **API Gateway**: 라우팅, 인증 검증, CORS, Rate Limit, 보안 헤더

### 프론트엔드 (모노레포 3개 패키지)
- **Customer App**: 고객 주문 인터페이스
- **Admin App**: 관리자 대시보드
- **Shared UI**: 공통 컴포넌트, 훅, 타입, 유틸리티

### 인프라
- **MySQL (RDS)**: 서비스별 스키마 분리, 단일 인스턴스
- **S3**: 메뉴 이미지 저장
- **ALB**: 트래픽 분산, SSL 종료

---

## 4. 핵심 설계 원칙

1. **데이터 소유권 분리**: 각 서비스는 자신의 데이터만 직접 접근
2. **API 계약 기반 통신**: 서비스 간 HTTP/REST로 명확한 인터페이스
3. **독립 배포**: 각 서비스는 독립적으로 배포/스케일링 가능
4. **실패 격리**: 한 서비스 장애가 전체 시스템에 전파되지 않도록 설계
5. **보안 계층화**: Gateway(인증 검증) + Service(권한 검사) 이중 보안
